# Modding the game from the decomp (prototype, proven end to end)

**What works today:** edit a C function, rebuild the disc, get a playable image where *only* your change differs from the
original. Proof (2026-09-30): changing the zodiac "best" bonus from +50% to +100% (one constant in
`battle_formula_apply_zodiac_compatibility.c`) produced a disc that differs from your original in **1 sector and 2 bytes**
(`port\tools\compare_discs.py`), with the sector checksums regenerated by the build.

## How

The opt-in modding build lives on the downstream branch `mod-build-path` (2 commits: the tool change and the example mod; patch
files in `patches\mod-build-path\`). It is **not** meant for upstream — upstream's tool deliberately refuses any difference.

```powershell
# in a checkout of the mod-build-path branch (currently the worktree .\fft_sweep; use FFT_REPO to point the helper at it)
$env:FFT_REPO = 'C:\Storage\Build\FFT Mod\fft_sweep'
# 1. edit any function under src\ (e.g. src\battle\battle_formula_*.c)
# 2. optionally preview the size fit / instruction change (~2 s):
.\fft.ps1 diff battle_formula_apply_zodiac_compatibility        # "does not match" is expected in mod mode; note the sizes line
# 3. build the modded disc
$env:TOOLS_MOD_MODE = '1'
.\fft.ps1 build disc                                             # prints MODIFIED (mod mode) <function> ...
# 4. see exactly what changed vs your original
python .\port\tools\compare_discs.py '.\game\Final Fantasy Tactics.bin' '.\fft_sweep\build\disc\output-scus-94221.bin' `
   --file 1000 1397096 0x80067000 BATTLE.BIN --functions .\fft_sweep\target\battle.yaml
Remove-Item Env:TOOLS_MOD_MODE
```

The result is `build\disc\output-scus-94221.cue/.bin` in that checkout — load it in any PS1 emulator (not installed here; downloading one
needs your OK). Without `TOOLS_MOD_MODE` the tool is exactly as strict as before.

## Limits (by design of the prototype)

* **A function may not grow.** It is patched into its original slot (padded with nops); a bigger function is refused with a clear
  message. Size-preserving or shrinking edits (constants, comparisons, rebalanced formulas, removed branches) work. Growth needs a
  code cave (redirect to new code placed in free overlay space) or a real relocation step — the next tooling milestone.
* `rodata` (string/constant tables emitted by a function) stays strict; data tables (item/job/ability stats) are not code and
  are not patched by this — they are changed by a data-patch layer (a text file of `module symbol+offset bytes`), not built yet.
  The native spikes show how to read those tables by symbol name from the disc image.
* Each module still has to keep its size; new overlays/files are not supported.

## Previewing a change without an emulator

The rules code also runs natively. Commit your edit on the mod branch, then `.\port\probe.ps1 -Rev mod-build-path` (re-portifies that
commit) and `.\port\native\attack.ps1` to see the new hit/damage numbers headlessly — **verified**: with the zodiac example the
no-crit damage goes from 216 to **288** (opposite signs + opposite sexes: XA 12 -> 24, x WP 12), average ~293, max 564. That makes
balance experiments fast: seconds, no disc, no emulator. (Run `.\port\probe.ps1` with no `-Rev` afterwards to go back to `HEAD`.)

## Hygiene

Keep mod branches separate from the cleanup branches; never commit game data; keep `master`-derived branches strict. To go back to
the pristine matching build, switch branches (or unset `TOOLS_MOD_MODE`) — `validate` and `build disc` on `master` still require
byte-exactness.
